2. 项目概述

2.1 项目背景

兴业银行现有贯标系统为自研单体应用，已配套数据字典系统。根据业务需求，智能贯标能力应作为辅助工具嵌入现有数据字典系统，而非独立建设。

在监管强化数据安全、模型合规和信创适配的要求下，需在不改变现有入口和流程的前提下，为”数据字典 + 贯标”场景提供可建议、可解释、可审核、可追溯的辅助能力。

2.2 现状问题

问题类型 具体表现
编制效率低 标准命名、定义、口径编制依赖人工，周期长
标准重复 不同条线对同一业务对象存在”近义不同名、同名不同义”问题
评审依赖经验 标准评审质量依赖专家经验，缺乏统一检查机制
知识未沉淀 历史标准、监管要求、业务术语缺乏统一语义映射
贯标率管理难 各业务系统贯标率考核前集中补录，效率低、质量不稳定

2.3 项目价值

受益方 价值
开发人员 降低找数、问数、重复建标成本
数据字典系统 从”被动查询”升级为”可推荐、可建标辅助”的主动服务
贯标体系 沉淀标准知识库、审核规则库、智能推荐能力
科技部门 构建符合信创要求、可私有化部署的能力底座
管理层 形成可量化、可追溯的提效成果

3. 项目目标

3.1 一期目标

基于现有数据字典系统，建设内嵌式智能贯标辅助能力：

  • 完成智能贯标核心闭环（不引入血缘数据库）
  • 建成可私有化部署的标准知识库
  • 接入 Qwen3 和 DeepSeek3 两类模型
  • 形成标准新增、变更、评审三类场景的智能辅助
  • 形成开发人员智能取数与建标建议能力
  • 形成接入系统贯标率分析与整改辅助能力
  • 与现有数据字典及贯标系统打通

3.2 成功指标

指标 一期目标 统计口径
智能取数命中率 ≥70% 命中可直接使用对象的查询数 / 总查询数
取数定位时长下降 ≥40% 上线前后典型查询定位时长对比
标准推荐采纳率 ≥45% 被人工采纳的推荐数 / 总推荐数
重复标准识别准确率 ≥80% 抽样复核正确数 / 系统判重数
智能纠错命中率 ≥75% 被认可的纠错建议数 / 总建议数
标准编制耗时下降 ≥30% 上线前后同类标准编制时长对比
评审工作量下降 ≥25% 标准评审工时对比
知识入库覆盖率 ≥80% 已纳入知识库的资料 / 应纳资料
接入系统贯标率提升 ≥15% 上线前后平均贯标率对比
低贯标率系统整改闭环率 ≥70% 治理周期内完成整改的系统数 / 低贯标率系统总数

4. 建设原则

原则 说明
嵌入优先 能力嵌入现有数据字典系统，不建独立入口
知识先行 先建设知识库和规则体系，再做模型增强
私有部署 模型、知识、日志、审计能力内网部署
信创兼容 应用、中间件、数据库、OS 采用国产兼容路线
人机协同 系统只给建议，不绕过人工审批
可追溯 每条推荐、判重、纠错结果可回溯到依据
小步快跑 一期聚焦知识库+推荐+判重+纠错核心能力

5. 项目范围

5.1 一期范围

类别 内容
知识建设 数据标准知识库建设、知识加工与清洗
系统改造 数据字典内嵌入口、贯标系统适配
智能能力 标准推荐、重复检测、智能纠错、智能取数、建标建议
流程支持 审核工作台、人工确认闭环、反馈回流
基础设施 模型服务管理、审计留痕、权限日志、统计看板

5.2 一期不做

  • 血缘数据库建设与血缘推理
  • 主数据、指标标准、数据质量平台
  • 面向终端客户的对话服务
  • 独立门户或工作台
  • 全自动发布（绕过人工审批）
  • 跨机构数据共享

6. 用户与场景

6.1 目标用户

角色 核心诉求
全行开发人员 快速找数、判断是否已有标准、减少沟通成本
标准管理员 提升编制效率、降低重复审核成本
数据架构师 全局视角、去重能力、规则收敛
科技管理人员 看板指标、提效成果、可汇报数据

6.2 核心场景

场景一：新增标准时智能推荐 - 输入候选标准信息 - 系统召回相近标准 - 返回推荐结论、理由、相似标准、置信度

场景二：评审时重复检测 - 自动检测同义重复、口径近似、语义相同

场景三：编写时智能纠错 - 自动校验命名规范、定义完整性、类型一致性

场景四：智能取数 - 自然语言查询 → 返回表/字段位置 → 无结果时生成建标建议

场景五：贯标率分析与整改 - 统计系统贯标率 → 识别未贯标对象 → 生成整改建议 → 跟踪整改进度

7. 业务方案

7.1 业务闭环

开发人员进入数据字典 → 发起查询/新增/评审 → 系统执行规则校验+检索+推理 
→ 返回建议和依据 → 人工确认 → 结果反哺知识库

7.2 贯标率提升闭环

采集系统元数据 → 计算贯标率 → 识别未贯标对象 → 生成整改任务 
→ 人工处理 → 回写状态 → 重新计算贯标率

7.3 核心能力模块

模块 说明 优先级
知识接入与加工 数据字典接入、文档解析、知识清洗 P0
标准知识库 存储结构化标准、非结构化文档 P0
规则引擎 命名/格式/一致性校验 P0
智能推荐引擎 检索增强 + 模型生成 P0
重复检测引擎 相似度检测、规则判重、语义判重 P0
智能纠错引擎 规则 + 模型纠偏建议 P0
智能取数引擎 表字段定位、建标建议 P0
贯标率分析引擎 统计覆盖率、识别缺口、生成建议 P0
审核工作台 人工确认、反馈、留痕 P0
模型服务治理 路由、审计、灰度、评估 P1
运营分析看板 采纳率、问题分布、知识覆盖率 P1

8. 技术架构

8.1 总体架构

采用”1个内嵌入口 + 1组服务中心 + 3个引擎 + 2类存储 + 1个模型网关”架构：

组件 说明
内嵌入口 数据字典系统中的智能贯标助手
服务中心 查询编排、推荐判重、纠错建标、审核反馈
智能引擎 推荐引擎、判重引擎、纠错引擎
存储 关系型数据库（主数据）+ 检索存储（全文/向量索引）
模型网关 统一接入 Qwen3、DeepSeek3

8.2 技术栈

层级 技术
前端 Vue 3（按行内组件体系）
后端 Java 17/21 + Spring Boot
AI 集成 Spring AI 或企业统一 SDK
规则引擎 Drools / Aviator / 自研
检索引擎 Elasticsearch / OpenSearch
关系数据库 openGauss、TDSQL（后续兼容 GaussDB）
缓存 Redis 或国产兼容
消息队列 RocketMQ / Kafka
模型推理 vLLM / SGLang / 行内统一平台
部署 K8s / OpenShift / 行内部署平台

8.3 数据库兼容

  • 当前主支持：openGauss
  • 并行兼容：TDSQL
  • 后续扩展：GaussDB

设计原则： - 核心 SQL 采用通用语法，避免绑定单一数据库方言 - 差异点通过 DAO 层封装 - 全文检索、向量检索能力外置

9. 知识库设计

9.1 知识源范围

知识源 类型 一期纳入
数据字典系统 结构化 是
历史标准库 结构化 是
管理制度文档 非结构化 是
业务术语表 结构化 是
监管制度 非结构化 是
专家经验样本 半结构化 是
元数据血缘 图谱 否

9.2 知识库分层

层级 说明
原始资料层 保存原始数据（字典表、制度文档等）
加工标准层 去重、结构化映射、版本标记、标签分类、文档切片
语义索引层 关键词索引、规则标签索引、向量索引、同义词索引
应用服务层 向业务系统提供统一知识服务接口

10. 智能能力设计

10.1 标准推荐

流程： 输入 → 关键词/同义词/向量召回 → 规则过滤 → 模型推理 → 输出

输出结构： - 推荐结论（复用/新增/合并/修改） - 候选标准 TopN - 推荐理由 + 相似度 + 命中规则 + 依据 + 风险提示

10.2 重复检测

三层判重： 1. 规则判重 — 名称/编码/属性完全一致 2. 近似判重 — 分词、同义词、编辑距离 3. 语义判重 — embedding + 模型判断

10.3 智能纠错

规则类型 检查项
硬规则 命名长度、禁用词、格式、类型一致性
软规则 定义完整性、术语一致性、表达歧义
模型推理 规范改写、差异提示、修订版本建议

10.4 智能取数

流程： 1. 自然语言输入 2. 识别业务对象、字段语义 3. 检索数据字典、标准库、知识库 4. 返回：已存在 → 表/字段位置 + 依据；不存在 → 建标建议

11. 风险与应对

11.1 项目风险

风险 概率 影响 应对措施
模型效果不达标 中 高 分阶段验收，效果不达标可回退人工流程
知识库质量差 高 高 建立质量标准和审核机制
数据字典接入延迟 中 中 提前确认接口，准备 Mock 数据
开源组件不合规 低 高 提前完成安全与许可证评估
进度延期 中 中 预留缓冲期，关键路径管理

11.2 技术风险

风险 应对
模型幻觉 强制检索增强、输出依据、人工复核
越权访问 检索前置权限过滤
知识污染 建立知识审核流程
数据泄露 模型输出可追溯、敏感数据分级

11.3 回退方案

如果智能能力效果不达标： 1. 可关闭智能推荐，回退到纯人工流程 2. 知识库仍可作为检索工具使用 3. 模型调用可降级为单模型或禁用

15. 建议结论

本项目按”数据字典内嵌、知识库先行、规则约束、模型增强、人机协同、私有部署、信创兼容”路线推进。

一期目标： 1. 建成标准知识库 2. 做出高可用的推荐、判重、纠错能力 3. 与现有数据字典系统形成闭环 4. 建立可审计、可持续优化的治理机制
