# 1.43 to v2 Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the real 1.43 panel data into the v2 panel with a repeatable, dry-run-safe script, starting with the 104 existing forward records.

**Architecture:** Use a two-stage pipeline: export the live MySQL data from 1.43 into a normalized JSON snapshot, then import that snapshot into the v2 SQLite database through a deterministic mapping layer. The migration keeps the current v2 installation intact by writing into a cloned test database first, and it treats `user`, `node`, `tunnel`, `forward`, and related relation tables as separate import units so failures can be isolated and retried.

**Tech Stack:** `bash`, `mysql`, `sqlite3`, `python3`, `jq` or Python JSON handling, Docker, SSH.

### Task 3: Build the v2 import mapper

**Files:**
- Create: `scripts/migration/import_v2.py`
- Create: `scripts/migration/mapping_rules.py`

- [ ] **Step 1: Implement source-to-target field mapping**

Map the old 1.43 tables into the v2 tables with explicit defaults:
- `user` -> `user`
- `node` -> `node`
- `tunnel` -> `tunnel`
- `forward` -> `forward` plus `forward_port` if the port relationship is required
- `speed_limit` -> `speed_limit`
- `statistics_flow` -> `statistics_flow`

Expected: every destination row is created from a pure function of source data and defaults.

- [ ] **Step 2: Handle fields that no longer exist**

For missing fields in v2, choose deterministic defaults:
- `node.remark`, `expiry_time`, `renewal_cycle`, remote fields -> `NULL` or empty string
- `tunnel.inx`, `ip_preference` -> `0` or empty string
- `forward.speed_id` -> `NULL` unless a matching speed limit exists

Expected: the import does not fail because of absent source fields.

- [ ] **Step 3: Preserve source identifiers**

Keep a source-id mapping table in memory or a sidecar JSON file so related rows remain connected:
- `forward.user_id`
- `forward.tunnel_id`
- `forward_port.forward_id`
- `forward_port.node_id`
- `group`/`permission` relations if they are later migrated

Expected: the importer can remap foreign keys consistently during a single run.
